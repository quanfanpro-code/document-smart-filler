## 一、背景与问题

现有两个系统功能重叠但各有硬伤：

| 系统 | 优点 | 硬伤 |
|---|---|---|
| Word文档智能提取系统（重型） | 四层容错、字段校验完善、多议题拆分强 | 一篇文档要和大模型对话2+N次、全文重复喂两遍，token消耗大、反馈慢；现有容错框架较重，新系统应精简结构，同时保留必要的字段类型、金额关系、来源和完整性检查 |
| word大模型填表系统（轻型） | 一篇文档只对话1次，快、省token | 零容错，模型多说一句废话就直接污染Excel；无超长保护；无断点续跑以外的恢复手段 |

目标：合并为一个新系统，以轻模式正常情况下每个可独立处理的单据或单据组一次模型请求为基础，吸收重型的模板能力和必要容错，针对四类财务/办公文档特化。重模式分段、多页边界识别和必要重试允许多次请求；减少重复输入是优化目标，不以牺牲完整性换取固定调用次数。

## 一·五、老系统的去向与零件复用清单

**两个老系统原封不动保留在原地，一行代码都不改**，随时能打开继续用——新系统不好用，手里永远有退路。

新系统是新建的独立项目（`项目根目录`），不从老项目里"连线引用"，而是把需要的零件**复制过来改造**，复制进来的代码就和老项目再无关系。

从《word大模型填表系统》（轻型）拆走的零件：

| 零件 | 拿来干什么 |
|---|---|
| word_reader.py（Word读取） | 复用正文与表格按原顺序读取的能力；改造.doc转换路径，在新系统工作目录转换，保留来源位置，不在源目录生成或覆盖文件 |
| excel_io.py（Excel读写、模板表头读取） | 写结果Excel、读用户的模板表头 |
| deepseek_client.py（模型调用） | 改造成连企业服务器的客户端（改默认地址/模型名、加图片传输能力、加2路并发排队） |
| pending_store.py（待写入缓存） | 参考已处理结果先落盘的思路；新方案必须解决写Excel与标记完成之间中断导致的重复写入，不能原样照搬 |
| archive.py（原始回答存档） | 模型每次说的原话落盘备查 |
| main_window.py（GUI骨架） | 界面底子：选文件、进度条、API配置区，在此基础上加"文档类型选择"和"需人工核对"查看 |
| processing_pipeline.py / worker.py（批处理流程） | 单文件处理流程和后台线程的骨架，按新流水线改造 |

从《Word文档智能提取系统》（重型）拆走的零件：

| 零件 | 拿来干什么 |
|---|---|
| template/parser.py（Excel模板解析） | 模板覆盖模式：解析用户给的模板表头 |
| output/excel_writer.py（模板写入） | 按用户模板格式写回Excel |
| extraction/response_parser.py（回答解析） | 仅参考剥离代码块、提取完整JSON等不改变字段值的处理；不复制把截断内容补成成功结果的逻辑，不整体搬入其字段校验框架 |
| document/word_reader.py、document/block_stream.py（结构读取） | 参考段落、表格和来源位置读取；实际代码并非完整的超长切段器，长文切段和合并需要在新系统实现 |
| 整体"先拆议题再逐块抽"的流水线思路 | 参考事项拆分；完整正文不为同一目的重复整篇输入，跨段衔接可有必要重叠，分段结果必须合并校验 |

**明确不整体复制的部分**：重型系统的四层校验框架、复杂错误码与审计字段体系，以及轻型系统的零容错解析器。采用精简实现，但保留防止错填、漏填、重复写入和无法追溯的必要检查；不以模型参数规模作为取消检查的依据。

## 二、用户与使用场景

- 用户：零编程基础的财务/办公人员，在 Windows 桌面使用
- 场景：把一批合同、会议纪要、发票、会计凭证批量转成 Excel 台账
- 使用动作：打开软件 → 选文档类型 → 选文件/文件夹 → 点开始 → 等进度条 → 拿 Excel

## 三、已确认决策（用户逐项拍板）

1. **智能双模式**：发票/会计凭证走轻模式，正常情况下一个可独立处理的单据或单据组一次请求；合同/会议纪要走重模式，按结构和长度拆分、抽取、合并。**按文档类型自动分工，用户无需选择模式**。输出行数按业务含义确定：发票每张一行；会计凭证每条分录一行并重复凭证字号、日期、核算单位等公共信息（用户2026-09-08单独确认）。
2. **文档范围**：合同、会议纪要、发票、会计凭证四类特化。共同读取、调用、校验和输出能力可复用；以后新增文档类型按实际业务补字段、输出规则和必要校验，不承诺只加字段包即可支持任意类型，也不为未提出的类型提前建立插件体系。
3. **文件形态**：Word（.doc/.docx）+ 图片/PDF。图像类使用用户已确认开通看图能力的企业模型服务，不接外部OCR；PDF由程序内部逐页转图片，文本型PDF同样受理。Word正文与表格按原顺序读取，存在影响取数的内嵌图片时进入图像处理，不静默遗漏。损坏、加密或实际无法读取的文件进入人工核对并说明原因。
4. **字段来源**：四类各内置一套默认字段（开箱即用）+ 保留Excel模板覆盖（用户给带表头的Excel就按用户表头抽）。
5. **地基**：在 `Code` 下新建项目，老代码当零件库复制改造（Word读取、Excel写入、模型调用、GUI、断点续跑等）；两个老系统原样保留不动。
6. **模型服务**：企业服务器 OpenAI 兼容接口——
   - Base URL：`（在本机设置中填写，公开版本不预置私人服务器地址）`（公开版留空，本机填写）
   - 模型名：`Qwen3.8-27B`（出厂默认，GUI可改）
   - API Key：需要，**不写死在程序里**，用户在GUI密钥框输入；可选"记住密钥"才存本地配置文件
   - GUI保留完整的在线API配置界面（地址/密钥/模型名均可改）
7. **界面**：桌面窗口（customtkinter，沿用老系统风格与零件）。
8. **容错档位**：适度容错——格式自动修复 → 修不好自动重问1~2次（更严格措辞）→ 彻底失败的行标记"需人工核对"，绝不静默混入正常数据；模型原始回答全部存档备查。
9. **输出**：一批一个Excel；默认正常结果在“提取结果”工作表，失败或内容可疑的结果在“需人工核对”工作表。模板模式保留用户业务表头及列顺序；模板工作表名称、写入位置、可保留的格式和辅助来源信息位置在方案设计中明确，不默认承诺支持任意复杂模板。只创建结果副本，不覆盖原始文档和模板。

## 四、我自主拍板的次要决策（如有异议看文档时提出）

1. **发票范围：凡票皆收**。增值税专票/普票/数电票、火车票、机票行程单、出租车票、定额发票、收据等全部受理——不限票种，模型看图现场识别票面内容，按内置字段能对上的对上，对不上的关键信息（票种、日期、金额、销售方等）也要尽量认出填上；原文未记载或不适用的字段允许留空；应有且原文存在但看不清、取数冲突或必需信息缺失的行进入“需人工核对”。内置字段以增值税发票为基准设计，其他票种靠模型现场发挥，不为每种票单独写规则。
2. **内置默认字段**（设计阶段细化定稿）：
   - 发票：票种、发票号码、开票日期、销售方、销售方纳税人识别号、购买方、购买方纳税人识别号、不含税金额、税额、价税合计、币种、金额单位、商品/服务明细
   - 会计凭证：核算单位、凭证字号、日期、分录序号、摘要、会计科目、借方金额、贷方金额、币种、附件张数
   - 合同：合同名称、编号、甲方、乙方、金额、币种、金额单位、含税口径、签订日期、履行期限、付款方式
   - 会议纪要：会议时间、地点、主持人、参会人员、议题、决议事项、待办事项、责任人、截止日期
   - 四类共同保留来源文件、页码或段落/表格位置、文件内单据或事项序号；人工核对结果另有具体原因。模板模式的附加方式在设计中定稿。以上字段按原文实际记载提取，不因字段存在而推测补齐。
3. **一个PDF含多张发票**：每张发票输出一行，不要求用户拆分文件；兼顾一页多票、一票跨页以及正文后附附件，不能把页数直接当作单据数。
4. **断点续跑**：保留已完成提取结果先落盘的能力；中途断电或关程序后，已保存结果不丢失、不重复，未完成部分继续处理，核对结果同样保存。Excel被占用时保留待导出结果，解除占用后继续导出；支持只重试失败项。源文件内容、模板或取数规则改变时，不混用旧缓存。
5. **并发**：服务器限制同密钥2路并发，程序内建排队，最多同时发2个请求，不催服务器。
6. **超长保护**：按用户提供的服务约束控制输入112K、输出16K、总量128K上限；预算包括提示词、正文、图像、必要重叠及服务实际计入的思考输出。采用保守余量并实测图片数和尺寸限制。超长文档自动切段，输出被截断时不得仅补括号当作完整成功，应缩小处理范围后重试；界面说明当前处理进度。
7. **思考模式**：轻模式优先关闭思考、重模式优先开启思考；实际开关、参数名、档位及输出预算以企业服务交付说明和真实请求验证为准，不把OpenAI兼容接口等同于支持固定reasoning_effort三档。

## 四·五、补充业务规则（2026-09-08评审意见已获批准）

1. **输出单位**：发票每张一行；会计凭证每条分录一行，公共字段重复，分录对应关系完整。合同以一份合同为汇总单位，分期付款不误当成多份合同；会议纪要保持议题、决议、待办、责任人及截止日期的对应。合同多笔金额和纪要多项待办的具体单元格或行组织方式在方案中展示样例后定稿。
2. **缺失值与格式**：区分“原文未记载”“不适用”“无法辨认”“来源冲突”；前两类按字段适用性允许空白，后两类保留可确认内容并进入核对。真实零值、负值按原文保留，不把空白变成零。编号与纳税人识别号按文本保存，保留前导零；金额按数值保存并保留币种、单位与原文口径，不自动汇率换算。
3. **必要校验**：检查字段类型、关键字段及来源位置；适用且三个金额都可确认时校验不含税金额加税额与价税合计；完整凭证在同一币种和口径下校验借贷合计。精度容差由原文计量精度确定，在方案中写明。校验不通过时不自动改平金额、不借用相邻单据的值补齐。不同票种按字段实际适用性检查，不要求收据具备增值税发票的全部字段。
4. **边界与合并**：同页多单据分别提取，跨页同单据合并，附件只为所选类型的单据提供相关信息，不自动生成其他类型台账。相同文字在不同单据出现不等于重复；长文切段保留来源位置及必要上下文。正文、附件、补充协议的数值或条款相互冲突时，列出冲突来源，不随意选一个版本。
5. **来源追溯**：每条输出能回到来源文件和页码，Word无法稳定提供页码时使用段落、表格及单元格位置；不能虚构页码。人工核对原因具体到无法辨认、金额关系不符、来源冲突、未完整处理或文件读取失败。只有某部分失败时，应保留其余可靠结果并报告未完成范围；整张凭证无法确认完整或平衡时，该凭证各分录一并进入核对。
6. **模板口径**：明确字段名称、字段含义、工作表、表头和写入起始位置。对“金额”等有歧义的字段允许填写取数说明；运行前展示识别结果，只在存在实际歧义时要求用户选择。明确首版对合并表头、样例行、已有数据、公式及格式的支持范围。模板无法按约定处理时说明原因，不静默改成另一种表格。
7. **恢复和导出**：批次绑定源文件内容、所选类型、模板、取数说明和模型配置；同一批次恢复前校验一致性。已确认结果在恢复时唯一存在，模型返回但尚未保存的部分允许重新请求，不冒充已经保存。只重试失败项后更新原结果，避免正常表和核对表同时留存同一结果。程序已有结果Excel被用户修改时保留该版本，另导出新副本；不把人工修改当作模型缓存。
8. **来源保护与可用性**：源文档及原模板只读。DOC转换、PDF转图、模型回答和运行状态存放在新系统自己的工作目录；开始后不因重复点击启动第二个同批次处理任务。界面显示已完成数、核对数、当前文件及处理阶段，完成时能打开结果文件和核对清单。

## 八、验收标准

1. 四类文档建立固定验收清单和经人工核对的标准答案；样本逐类覆盖常规情况、字段缺失、模糊、损坏、多单据和跨页/跨段情况。样本数量、精确比较规则及质量阈值在设计中列为明确验收条件；未提供真实样本时，合成样本测试不能替代真实业务验收。
2. 分别报告关键字段准确率、整行正确率、单据/分录数量、漏检及重复数、需人工核对比例、正常样本自动完成比例，说明各自分母；避免用大量转人工掩盖提取能力不足。
3. 默认字段与模板字段均验证实际取数口径；正常结果满足适用字段及必要校验，允许有依据的空白，无模型解释性废话混入，不凭空补税额、币种、责任人或日期。
4. 真实扫描件、图片和PDF能够提取关键字段；同时验证一页多票、一票跨页、凭证附件、多页凭证分录、混合图文Word和文本型PDF的处理范围。
5. 一张“一借多贷”的凭证按分录数输出多行，公共字段一致，借贷对应及汇总正确；核对状态按完整凭证判断。会议待办、责任人及期限不得错配；合同分段结果保留对应关系。
6. 损坏、模糊、源文冲突、金额关系不符和模型输出截断时，可靠部分可保留，未完成范围或可疑结果进入人工核对并带来源及原因。零值、负值、前导零、长编号、币种和金额单位按约定保留。
7. 用含10张票的PDF在处理中途退出并恢复，最终10张票的结果各存在一次；分别覆盖提取已保存但Excel未写入、Excel已写入但完成标记未更新的中断时点，以及只重试失败项。
